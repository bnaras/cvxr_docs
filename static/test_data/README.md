# Regression baselines

Saved results for the example and reference documents, one directory per CVXR
version. Each `<version>/<data_dir>/` holds the `.RDS` files that document
writes in `save` mode and compares against in `test` mode; `<data_dir>` is the
document's own `data_dir` YAML parameter.

```
static/test_data/
  1.8.2/    63 documents   CVXR 1.8.2
  1.9.1/    64 documents   CVXR 1.9.1 + clarabel 0.11.2   (2026-08-14)
  1.9.2/    65 documents   CVXR 1.9.2 + clarabel 0.11.3   (2026-08-22)
  1.9.3/    65 documents   CVXR 1.9.3 + clarabel 0.11.3   (2026-10-14)
  1.9.3-1/  83 .RDS        CVXR 1.9.3-1 + clarabel 0.11.3 + scs 3.3.1   (2026-11-23)
```

`1.9.3-1/` is the set the documents check against: every `.qmd` carries
`testdata_dir: test_data/1.9.3-1` as of 2026-11-24. It holds the same 83 `.RDS`
names as `1.9.3/`. A save pass on 2026-11-23 under the CVXR 1.9.3-1 release
candidate, clarabel 0.11.3, scs 3.3.1 and Uno 2.9.2-2 wrote 72 of the 73
documents. Two followed on 2026-11-24:

* `dnlp_tutorial/` (5 files). The document's `entropy` chunk failed with
  "Solver UNO failed", under CRAN CVXR 1.9.3 too: CVXR's Uno interface did not
  evaluate the problem at the starting point before the solve, and Uno's
  `"ipopt"` preset asks for a gradient first. CVXPY 1.9.3 fails the same way
  with `uno_ipm`. Saved under 1.9.3-1 with that fixed (ADR D_PORT.21 in the
  CVXR development repository).
* `miqp/miqp.RDS`, re-saved when the document moved from GUROBI to SCIP (scip
  1.10.1-1). Same integer solution; optimal value 25.6092300163 against
  GUROBI's 25.6092300021, and `x` within 4e-8 of integers, outside the
  document's 1e-10.

Test renders of those two documents against `1.9.3-1/` pass. A full `test`
pass against the whole set has not been run yet.

`1.9.3/` was the set the documents checked against from 2026-10-14 to
2026-11-24. It holds the same 83 `.RDS`
as `1.9.2/`, generated by a save pass under development CVXR 1.9.2.9205, with
`plasso/plasso.RDS` regenerated under 1.9.2.9206 after the document fix below.
A `test` pass against it rendered 73/73 clean at 1.9.2.9213. It was then
checked against a fresh save pass under a 1.9.3 release candidate: all 496
values in the 83 files were exactly equal, so it was kept as the 1.9.3 record
rather than regenerated (the release-built copy was discarded).

One file was regenerated under released CVXR 1.9.3 on 2026-10-17:
`glmnet_equivalence/glmnet_equivalence2.RDS`. The document draws its second
response `y2` with `sample()` *after* its first `psolve()`. Through 1.9.2 a
solve consumed random draws (the compiled canonicalizer drew an internal
label from R's stream), so the saved value belonged to a `y2` that 1.9.3,
whose solves leave the stream alone, no longer produces (48 of 100 labels
differ). Fitting the second problem on the old draw reproduces the old file
exactly; the new file is the fit on the draw the document now makes. The
first problem, whose data precede any solve, is unchanged.

`1.9.2/` holds 83 `.RDS`, one more
than `1.9.1/` — the extra is `dgp_not_a_gp/not_a_gp1.RDS`, added 2026-08-25
with the `examples/dgp/when-its-not-a-gp.qmd` example, generated under the same
CVXR 1.9.2 + clarabel 0.11.3 pairing and verified by a `test` pass. `1.9.1/`
has no counterpart for it, so that set is now one document short of the
documents in the tree.

Of the 82 shared with `1.9.1/`, the last to be generated was
`dqcp_concave_fractional/concave_fractional1.RDS`, written 2026-08-22
after the document pinned `solver = "SCS"`: with the default solver that
example (`maximize sqrt(x)/exp(x)`) errors with "Max iterations hit during
bisection" — **CVXPY 1.9.1 and 1.9.2 fail identically with their default**,
and CVXR 1.9.1 was the outlier for succeeding. The cause is that bisection's
feasibility subproblems become marginally infeasible near the optimal ratio,
where Clarabel ends in `NumericalError` instead of certifying; SCS and ECOS
certify cleanly. The document now says so.

Verified after generation: a `test` pass against `1.9.2/` renders clean —
71/72 in the bulk run plus the regenerated document individually (its two
`expect_equal` at 1e-10 observed passing in the rendered output). A baseline
set that has not been checked against itself has not been checked.

## Provenance

**A baseline is only meaningful together with the solver that produced it.**
The assertions in these documents run at `tolerance = 1e-10`, and 51 of them are
`expect_identical`, which is far tighter than the difference a solver version
bump can introduce. `1.9.1/` was generated with **clarabel 0.11.2** — the version
on CRAN when CVXR 1.9.1 was current — deliberately, and not with the newer
0.11.3 that may be installed in the default library. Pair them when you
regenerate or the diffs you see will be Clarabel's, not CVXR's.

Determinism also depends on the project `.Rprofile`, which excludes
MOSEK/GUROBI/CPLEX/SCIP/XPRESS from *automatic* solver selection. Without it,
CVXR picks the highest-priority installed solver, and a machine with commercial
solvers produces baselines that no other machine reproduces. A document that
names a solver explicitly still gets it.

## Regenerating, or adding a version

```r
## from the repository root
source("static/test_harness/set_render_mode.R")   # NOTE: sourcing calls set_params()
set_params("save", testdata_dir = "test_data/<version>")
```

then render the documents, then `set_params("ignore")` before committing so the
published site does not carry harness state.

Two things bite:

* **`dir.create()` in the save chunks is NOT recursive.** `static/test_data/<version>/`
  must exist first, or every document errors on its first save.
* **Select the CVXR being tested through the library path, not by installing over
  the default one.** Point `R_LIBS_USER` at a directory holding that CVXR *and*
  its matching clarabel; everything else falls through to the system library.

Render documents one at a time rather than as a whole site when testing: in
`test` mode a failed expectation errors the render, and a site render aborts at
the first error, so you would see only the earliest failure instead of all of
them.

## What differs between versions

`1.8.2` → `1.9.1` differs in 3 of 63 documents, and the reasons are known and
benign. `1.9.1` → `1.9.2` differs more widely — chiefly because 1.9.2 aligns
SCS's acceleration defaults with CVXPY's, which moves numbers at the ~1e-5
level across every SCS document, against assertions written at
`tolerance = 1e-10`. Two further differences are structural rather than drift:

* `dqcp_hypersonic_shape` — the `1.9.1` baseline records **1.3**; the truth is
  **0.14589815**. A DQCP canonicalization fix in 1.9.2 corrected it, so the old
  baseline was recording a wrong answer.
* `linear-program` and `quadratic-program` — `dual_value` changed shape from a
  bare `numeric(n)` to an `n x 1` matrix. This is a FIX: 1.9.1 returned
  `value()` as `n x 1` and duals as a plain vector, which was internally
  inconsistent; 1.9.2 makes duals follow the same 2-D convention. (CVXPY
  returns `(n,)` for both, because numpy is 1-D-native and CVXR is not.)

`1.9.2` → `1.9.3` differs in 2 of 83 files (11 of 496 values):

* `fast-mixing-mc` — CVXR 1.9.3 makes `cvxr_norm(X, 2)` and `norm(X, "2")`
  of a matrix the largest singular value, as base R and CVXPY do; 1.9.2
  returned the Frobenius norm. The example minimizes the spectral norm
  `cvxr_norm(P - 1/n, "2")`, so `1.9.2/` was recording the wrong problem.
* `dgp_not_a_gp` — drift of at most 1.6e-8, which the document's
  `expect_identical` catches; not yet traced.

`pliable-lasso` was the third: its `sum(cvxr_norm(theta, 1))` on a p x K
matrix became the max column sum under the same 1.9.3 change, where the text
means the entrywise L1 penalty. It now reads `norm1(theta)`, which reproduces
the `1.9.2/` results within 1e-10, and its assertion -- commented out until
2026-10-14, so the document had checked nothing -- is restored as
`expect_equal(..., tolerance = 1e-10)`.

`1.9.3` → `1.9.3-1` differs in 16 of 83 files, and 14 of them fail the
documents' 1e-10 comparisons:

* 13 files of 11 documents that solve with SCS: antenna-array, clock-mesh,
  nonneg-matrix-fact, robust-kalman, tv-inpainting (2 files),
  structured-prediction (2), concave-fractional, fast-mixing-mc, log-concave,
  sdp and sparse-inverse-covariance-estimation. Relative to each value's
  largest entry, the differences run from 2e-7 to 3e-4, except two: in
  clock-mesh an area is 12.88 against 13.10, and in log-concave a pmf entry is
  0.0197 against 0.0220. Two changes are mixed in these files, and they have
  not been separated file by file:
  * CVXR 1.9.3-1 leaves SCS's `acceleration_interval` at SCS's own default,
    5, where 1.9.3 set 10. That alone moves SCS's results within its
    tolerance. On the TV in-painting example of the useR! 2026 tutorial,
    1.9.3 gives 740.1373 and 1.9.3-1 gives 740.1372, and passing either
    value to the other version reproduces the other's result exactly.
  * CRAN CVXR 1.9.3, which still sets 10, also fails these documents against
    `1.9.3/` under today's libraries, and scs 3.3.2 changes nothing. So part
    of the change came from outside CVXR after `1.9.3/` was last verified
    (2026-10-17), and that part has not been traced.
* `miqp/miqp.RDS`: the move to SCIP, above.
* `dnlp_tutorial/duals.RDS` and `quadform.RDS`: 8e-16 and 3e-11, within the
  documents' tolerances.

The measurements, and the analysis of each difference, are recorded in the CVXR
development repository at `notes/docs_regression_baselines.md` and
`notes/docs_baseline_diff_1.9.1_vs_1.9.2.md` — not repeated here, so there is
one owner for those numbers.
